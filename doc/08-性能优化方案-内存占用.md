# 内存占用优化方案

## 1. 背景与结论

针对"内存占用过高"的问题，对主进程（`src/main/`）与渲染进程（`src/renderer/src/`）代码做了一次专项调研，逐一核对了 Zustand store、数据库驱动、Monaco Editor 生命周期、连接池、ER 图状态、图片处理等模块。

**结论先行**：本项目当前最大的内存风险点是**任意 SQL 查询结果无行数上限、且结果会随未关闭的 tab 长期驻留内存**；其余模块（日志、任务历史、Monaco 释放、ER 图状态、头像图片）基本已经处理得当。WeakMap/WeakSet 能在少数"元数据关联"场景上提供更安全的自动回收，但**不能替代对大结果集本身的裁剪**——这一点在第 4 节详细说明，避免技术选型上的误用。

## 3. 需要优化的问题（按优先级排序）

### 3.1 【P0】SQL 查询结果无行数上限

**问题**：

- `src/main/db/driver/pg/PostgreSQLDriver.ts`（约 L753-776）与 `src/main/db/driver/mysql/MySQLDriver.ts`（约 L534-560）的 `runQuery` 直接把 `pool.query()` 返回的全部行放进 `QueryResult.rows`，没有任何行数上限或流式读取。
- 用户执行一条不带 `LIMIT` 的 `SELECT *`（十万行级别）时，全部行会先在主进程内存中物化，再经 IPC 序列化整体传给渲染进程。
- `ResultTable.tsx` 用 `useVirtualizer` 做了虚拟滚动，但那只解决"渲染 DOM 节点"的问题，`result.rows` 这个 JS 数组本身仍然整份留在堆内存里。

**方案**：

- 在驱动层加一个硬性行数上限（如 `MAX_RESULT_ROWS = 50_000`），超过则截断返回，并在 `QueryResult` 上附加 `truncated: true` 标记。
- 渲染层在 `truncated` 为真时提示"结果已截断至 N 行，请添加 LIMIT 缩小范围，或使用导出功能获取全部数据"。
- 这是**收益最大、改动最小**的一项，建议第一优先做。

**权衡**：用户一次性查看"全表"的能力受限，但这本来就不该无限制地塞进内存和 DOM。

### 3.2 【P1】查询结果随未关闭 tab 长期驻留

**问题**：

- `src/renderer/src/store/workspaceStore.ts`（约 L284-288）的 `setQueryResult` 把结果整体存进 `tab.result`。
- 只要 tab 不关闭，即使用户切换到其他 tab，该结果仍完整保留在 store 内存中；多个大结果集 tab 同时打开时内存会叠加。

**方案**：

- tab 切换为非激活状态一段时间后，惰性释放其 `result`（只保留 SQL 文本和分页/游标信息）；重新切回时提示"结果已释放，请重新执行查询"或自动重跑。

**权衡**：牺牲"切回旧 tab 立即看到上次结果"的体验，用可控的重新查询成本换取内存上限。建议在 3.1 落地并观察效果后再决定是否需要做这一项。

### 3.3 【P2】连接池按数据库维度不随 tab 关闭释放

**问题**：

- `PostgreSQLDriver.ts` / `MySQLDriver.ts` 内部用 `pools: Map<string, Pool>` 按数据库名维护连接池（pg `max: 5`，MySQL `connectionLimit: 5`）。
- 只有整个连接（`connectionId`）执行 `disconnect()` 时才会遍历清空所有池；用户在同一个连接下切换浏览多个数据库时，各数据库对应的池会持续累积，不会随对应 tab 关闭而释放。

**方案**：

- 关闭某数据库对应的最后一个 tab 时，检测该 database 在当前连接下是否还有其他 tab 在使用，若无则单独对这一个 `Pool` 调用 `pool.end()` 并从 `pools` 中删除。

**权衡**：改动集中在驱动层，风险可控；由于单个池连接数本身不大（max 5），此项优先级低于 3.1、3.2，可作为后续收尾项。

### 3.4 【P3】单个 AI 对话内部消息/工具调用历史无上限

**问题**：

- `src/renderer/src/store/conversationStore.ts`（约 L268、L287-340）的 `turns` 数组只在切换/新建对话时清空（`selectConversation`/`createConversation`），**同一个对话内部**的会话轮次和每轮的 `toolCalls`（可能包含较大的工具执行结果文本）没有上限或裁剪。
- 长对话 + 多次工具调用会让历史文本持续堆积在渲染进程内存中。

**方案**：

- 优先级最低，先不动。若后续出现"AI 面板越用越卡"的用户反馈，再考虑给单个对话加轮次上限，或对较早的工具调用结果做摘要化/截断存储。

**实施状态（010-memory-optimization）**：未采用"裁剪/摘要化历史"方案——`turns` 数组本身不做任何截断，历史完整保留。改为在对话轮次达到 40 轮时，于输入框上方展示"建议新建对话"提示（[ConversationView.tsx](../src/renderer/src/components/code/ConversationView.tsx) 的 `CONVERSATION_LENGTH_NOTICE_THRESHOLD`），由用户自行决定是否新建对话来控制单个对话的内存占用，忽略提示不影响继续对话。

## 4. 关于 WeakMap / WeakSet 的适用性

WeakMap/WeakSet 的核心价值是：**用对象引用做 key，且不阻止该对象被垃圾回收**——适合"给一个对象挂载额外元数据，元数据的生命周期应该完全跟随对象本身，不需要手动清理"的场景。

### 4.1 为什么本项目大多数 store 不适合直接改成 WeakMap

调研发现，本项目里几乎所有会增长的状态（`nodePositions`、`pools`、`runsMap`、`tab.result` 等）都是用**字符串 ID**（`tabId`、`connectionId`、`database` 名）做 key 的 `Map`/`Record`，而不是对象引用。这是有意为之，而非疏漏：

- Zustand 的状态需要能被 React 组件订阅、能在 DevTools 里查看、部分还需要持久化（如 workspace 布局）——WeakMap 不可枚举、不可序列化，天然不支持这些需求。
- WeakMap 的自动回收时机由 V8 GC 决定，不可预测、不可控，无法保证"用户点击关闭 tab 的瞬间"内存立即释放——3.1/3.2/3.3 这类问题恰恰需要**主动、确定性**地释放（用户点了关闭，就应该立刻放掉），用 `delete map[tabId]` 这种显式操作比等 GC 更合适。

因此，把现有的 tabId/connectionId 索引结构改成 WeakMap **不会解决 3.1~3.3 里描述的问题**，反而会牺牲现有的可调试性和确定性释放能力。这一点需要明确，避免技术选型上的误用。

### 4.2 真正适合引入 WeakMap/WeakSet 的点

以下几处是"给对象挂载可丢弃的缓存/标记"场景，符合 WeakMap/WeakSet 的设计初衷，且属于本项目代码中真实存在的结构：

**(1) Monaco 补全元数据缓存 —— `src/renderer/src/lib/monaco/completionProvider.ts`**

现状：`provideCompletionItems` 每次触发补全（几乎每次按键）都会重新调用 `collectSchemaMetadata` 全量遍历一次 `connectionStore` 里的 schema 树（`L241-315`），没有任何缓存。

优化：引入 `WeakMap<monaco.editor.ITextModel, { version: number; meta: SchemaMetadata }>`，以当前 `model` 为 key 缓存上一次计算结果，并用 `model.getVersionId()` 判断内容是否变化决定是否重新计算。好处：

- 性能：避免每次按键都重新扫描整棵 schema 树；
- 内存：缓存跟随 `model` 对象存活，SQL 编辑器/DDL 弹窗关闭、`model` 被 dispose 后，缓存条目自动随之被 GC，不需要额外写清理逻辑，也不会像 `Map<string, ...>` 那样在忘记 `delete` 时造成累积泄漏。

**(2) 大结果集的行级临时标记（选中行/已校验错误行）**

如果后续要给 `ResultTable.tsx` 加"已选中""校验失败"这类行级标记，建议直接用行数据对象本身做 key：`WeakSet<RowRecord>`（或 `WeakMap<RowRecord, Meta>`），而不是用行下标 `index` 做 `Set<number>`/`Map<number, ...>`。

好处：一旦用户重新执行查询、`result.rows` 被整体替换为新数组，旧的行对象不再被任何地方引用，标记会随之自动消失；而用 `index` 做 key 则完全不会自动失效，必须在每次查询完成后手动 `clear()`，否则会出现"新结果的第 3 行莫名被标记为已选中"这类错乱，也会在忘记清空时持续占用内存。

**(3) 未来虚拟列表行元素的 DOM 级元数据（预留，当前不需要改）**

`ResultTable.tsx`/`ImportDataDialog.tsx` 目前用的 `@tanstack/react-virtual` 内部已经用测量索引管理元素高度，不需要额外改造。但如果未来需要给虚拟列表的行 DOM 元素挂载自定义元数据（例如做过某种昂贵计算的缓存结果），应该用 `WeakMap<HTMLElement, Metadata>`，而不是 `Map<index, Metadata>`——因为虚拟滚动场景下同一个 `index` 会被不同的 DOM 元素复用，用 `index` 做 key 容易张冠李戴，用元素引用做 key 则不会。

### 4.3 结论

WeakMap/WeakSet 建议只用在 4.2 列出的"缓存/标记跟随对象存活"场景，作为**代码健壮性上的加分项**；它们不能、也不应该被当作解决 3.1（大结果集本身占用）这一核心问题的手段。真正要降内存，还是要先做 3.1 的行数上限截断。

## 5. 建议实施顺序

| 顺序 | 事项                           | 对应章节 | 改动量 | 预期收益              | 实施状态                                       |
| ---- | ------------------------------ | -------- | ------ | --------------------- | ----------------------------------------------- |
| 1    | 查询结果行数上限截断           | 3.1      | 小     | 高                    | 已完成（010-memory-optimization US1）          |
| 2    | 非激活 tab 惰性释放结果        | 3.2      | 中     | 中高                  | 已完成（010-memory-optimization US2）          |
| 3    | Monaco 补全元数据 WeakMap 缓存 | 4.2 (1)  | 小     | 中（性能+内存双收益） | 未实施，本次不在范围内，仍为后续可选加分项      |
| 4    | 连接池按数据库维度释放         | 3.3      | 中     | 中                    | 已完成（010-memory-optimization US3）          |

建议先落地第 1 项并验证效果（用大结果集查询实测内存曲线），再决定是否继续推进后续项。

第 1、2、4、5 项已随 `specs/010-memory-optimization` 功能全部落地（第 5 项以提示引导代替历史裁剪，详见 3.4 节"实施状态"）；第 3 项（Monaco WeakMap 缓存）不在该功能范围内，仍是未来可选的性能优化项。
