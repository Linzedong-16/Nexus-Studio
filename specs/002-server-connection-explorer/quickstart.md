# Quickstart: 验证数据库服务器级连接与结构树重构

前置条件：本地或可访问的 PostgreSQL 服务器，且该服务器上至少有 2 个数据库（其中至少一个非空，含若干表/视图/函数/存储过程），用于验证"一次连接、多库浏览"与结构树层级还原。

## 环境准备

```bash
pnpm install
pnpm run dev
```

## 验证场景 1：一次连接访问整台服务器（对应 User Story 1 / FR-001~FR-005）

1. 在 Work 模式新建连接标签页，填写目标服务器的主机、端口、用户名、密码；"数据库"栏留空或填入任意一个数据库名，保存并连接。
2. 观察：连接表单不要求提前从下拉列表锁定唯一数据库即可连接成功。
3. 展开侧边栏中新建立的服务器节点，确认能看到该服务器上账号有权限访问的**全部**数据库（与实际数据库数量一致），而不仅是表单中填写的那一个。
4. 依次展开两个不同的数据库节点，确认互不影响、无需新建第二条连接。
5. 点击断开连接，确认该连接下所有数据库的展开状态与缓存一并清空；重新点击连接，确认可重新加载。

**通过标准**：对照 `spec.md` Acceptance Scenarios 1-4（User Story 1）逐条核对。

## 验证场景 2：结构树层级与真实数据一致（对应 User Story 2 / FR-006~FR-009）

1. 展开服务器节点 → 数据库节点 → Schema 节点，对照参考设计图核对层级顺序：服务器 → 数据库 → （Query、Schema…）→ Schema 展开后为 Query、Tables、Views、Functions、Procedures。
2. 打开 Tables/Views 分组，核对表/视图数量与名称同数据库管理工具（如 `psql \dt`、`\dv`）中的结果一致。
3. 展开一个尚未加载的节点时观察是否出现加载中提示；断开网络或使用错误权限账号触发一次加载失败，确认该节点单独显示错误与重试，其余已展开节点不受影响。
4. 使用刷新入口后，在服务器上新增/删除一个数据库（或表），确认刷新后结构树能反映最新结果。

**通过标准**：对照 Acceptance Scenarios 1-4（User Story 2）与 SC-002、SC-003、SC-004。

## 验证场景 3：PostgreSQL 专属模块隔离与查询入口（对应 User Story 3 / FR-010~FR-012）

1. 核对 Query、Functions、Procedures 三个分组只出现在 PostgreSQL 连接的 Schema/数据库层级，且与 Tables、Views 并列但来源独立（走查 `src/renderer/src/config/databaseCapabilities.ts`，确认它是唯一决定这些节点是否渲染的地方）。
2. 点击数据库层级的 Query 快捷入口，确认打开一个以该数据库为上下文的新查询标签页；点击某 Schema 下的 Query 入口，确认打开的标签页带有该 Schema 上下文。
3. 展开 Functions/Procedures 分组，核对列表名称、参数签名与数据库中的真实函数/存储过程一致（可用 `\df` 对照）。
4. 走查 `contracts/database-capabilities.md` 的扩展规则：确认新增数据库类型只需改动能力配置与该类型自身驱动文件（本期无需真正新增第二种类型，走查代码组织即可）。

**通过标准**：对照 Acceptance Scenarios 1-3（User Story 3）与 SC-003、SC-006。

## 验证场景 4：既有功能不回归（对应 FR-014~FR-016，SC-005）

1. 双击 Tables/Views 下的某个表，确认仍能打开查询标签页并执行 `SELECT * FROM ... LIMIT 100`，结果与调整前一致。
2. 在查询标签页手动编写 SQL 并执行，确认执行结果、耗时展示、错误提示均与调整前行为一致，且工具栏能明确显示当前查询作用于哪个数据库。
3. 找一条改造前保存的历史连接（绑定单一数据库），确认无需任何手动操作即可继续连接使用，且原绑定的数据库自动成为该服务器连接下默认展开/激活的数据库节点。
4. 运行质量门禁：

   ```bash
   pnpm run typecheck
   pnpm run lint
   pnpm run format
   ```

**通过标准**：三项命令全部通过；场景 1-3 手动走查全部符合预期，无回归。
