# Feature Specification: 数据库服务器级连接与结构树重构

**Feature Branch**: `002-server-connection-explorer`

**Created**: 2026-08-09

**Status**: Draft

**Input**: User description: "优化新建数据库连接的UI操作逻辑，具体要求如下：1. 修改数据库连接创建流程，将当前"连接到数据库服务器中具体某个数据库"的逻辑调整为"直接连接到数据库服务器"，实现一次性服务器级别的连接，避免每次仅连接单个数据库的操作模式。2. 重构侧边栏数据库连接及配置的文件树状图区域，按照设计图样式实现：正确渲染数据库服务器连接信息及层级结构；对接数据库驱动以动态获取并展示服务器级别的数据信息；特别处理 PostgreSQL 数据库特有的"Query"、"Functions"和"Procedures"模块，确保这些 PostgreSQL 专属功能与其他数据库通用功能隔离开来；设计可扩展的架构，以便未来接入其他数据库类型时能够灵活适配不同数据库特有的功能模块。3. 确保数据库连接逻辑修改后，所有相关功能（包括但不限于查询执行、数据浏览、连接管理）仍能正常工作，且用户体验流畅。"

## 特性概述

当前应用中，一个已保存的数据库连接只对应服务器上的某一个具体数据库，用户若要访问同一服务器上的其他数据库，必须重复创建多条连接配置。本特性将连接的语义调整为"服务器级连接"：用户配置一次连接（主机、端口、认证信息）即可访问该账号在该数据库服务器上有权限查看的全部数据库，无需为每个数据库单独建立连接。与之配套，侧边栏的结构树需要重新组织为"服务器 → 数据库 → 结构模块（Schema、表、视图，以及 PostgreSQL 特有的 Query / Functions / Procedures）"的层级，结构信息通过数据库驱动动态获取，并且专属模块的展示方式要为未来接入其他数据库类型预留清晰的扩展点。改造过程中，现有的查询执行、数据浏览、连接管理等能力必须保持可用，不能因为连接语义调整而退化。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 一次配置，访问整台服务器 (Priority: P1)

用户新建一个数据库连接时，只需填写服务器地址、端口与认证信息并完成"保存并连接"，而不必事先指定或绑定某一个具体数据库。连接成功后，用户能够在侧边栏看到该服务器上所有其账号有权限访问的数据库，并可自由在这些数据库之间浏览，无需为每个数据库重复创建连接。

**Why this priority**: 这是本次改造的核心诉求——把连接对象从"单个数据库"提升为"整台服务器"，是后续侧边栏结构树重构与所有下游浏览、查询能力的前提，没有它其他改动都无从谈起。

**Independent Test**: 使用一个拥有多个数据库的 PostgreSQL 服务器新建一条连接并保存连接，验证：①连接表单不要求预先锁定单一数据库为访问范围；②连接成功后能看到服务器上全部（有权限的）数据库，而不是仅一个；③无需新增第二条连接配置即可切换浏览另一个数据库。

**Acceptance Scenarios**:

1. **Given** 用户在新建连接表单中填写了正确的主机、端口、用户名、密码，**When** 用户点击"保存并连接"，**Then** 系统建立一次服务器级连接，且不要求用户在建立连接前从下拉列表中选定唯一目标数据库
2. **Given** 一条连接已成功建立，且该服务器上存在多个数据库，**When** 用户查看该连接下的可访问数据库，**Then** 系统展示该账号在服务器上有权限访问的全部数据库，覆盖率 100%
3. **Given** 用户已连接的服务器上有 A、B 两个数据库，**When** 用户从浏览 A 切换到浏览 B，**Then** 系统直接在同一条连接下切换，无需用户创建新的连接配置或重新输入认证信息
4. **Given** 用户点击断开该连接，**When** 断开操作完成，**Then** 该服务器连接下所有数据库的浏览状态一并断开/清空，且用户可随时重新连接

---

### User Story 2 - 侧边栏结构树按服务器层级正确展示 (Priority: P1)

用户在侧边栏的连接结构区域，能够看到与参考设计一致的层级：最上层是服务器连接节点（含连接标识与状态），展开后是该服务器上的数据库列表；展开某个数据库后，能看到该数据库下的结构分组（如 Schema、表、视图），且这些分组数据均来自对目标数据库驱动的实时查询，而不是静态占位。

**Why this priority**: 结构树是用户浏览与定位数据的主要入口，若树状层级与真实服务器结构不一致，用户将无法有效使用连接能力，因此与 Story 1 同为最高优先级。

**Independent Test**: 连接一个真实的 PostgreSQL 服务器（含多个数据库），逐层展开服务器 → 数据库 → Schema 节点，核对每一层展示的名称、数量与数据库中的真实数据完全一致；对未展开的节点不应提前发起数据请求。

**Acceptance Scenarios**:

1. **Given** 服务器连接已建立，**When** 用户查看侧边栏，**Then** 树状图第一层展示该连接的服务器节点，含连接名称/地址及连接状态
2. **Given** 用户展开服务器节点，**When** 展开完成，**Then** 第二层动态列出该服务器上的全部数据库，名称与数量与服务器真实数据一致
3. **Given** 用户展开某个数据库节点，**When** 展开完成，**Then** 系统通过数据库驱动实时获取该数据库下的结构分组（Schema、表、视图等）并正确渲染，未展开的其他数据库不受影响、不发起多余请求
4. **Given** 结构数据正在加载，**When** 加载尚未完成，**Then** 对应节点显示明确的加载中状态；**When** 加载失败，**Then** 节点显示明确的错误状态并支持重试，不影响树中其他节点的展示

---

### User Story 3 - PostgreSQL 专属模块隔离且架构可扩展 (Priority: P2)

用户在浏览 PostgreSQL 数据库/Schema 时，能在结构树中看到 PostgreSQL 特有的"Query""Functions""Procedures"节点，这些节点与"Tables""Views"等通用模块并列展示但来源独立。当未来项目接入其他数据库类型时，新数据库类型的专属模块（或缺失这些模块）能够独立配置，不会误显示 PostgreSQL 专属节点，也不需要改动已有 PostgreSQL 的展示逻辑。

**Why this priority**: 这是达成"设计图还原度"与"可扩展架构"要求的关键，但依赖 Story 1、2 建立的连接与树状骨架才能落地，且当前项目仅实现 PostgreSQL 驱动，实际可验证的多类型场景有限，因此定为 P2。

**Independent Test**: 在 PostgreSQL 连接下核对 Query/Functions/Procedures 节点按设计图位置出现；通过代码/配置走查确认这些模块的可用性由"数据库类型能力"决定，而非硬编码在通用树组件中，为后续新增数据库类型只需新增该类型的模块配置。

**Acceptance Scenarios**:

1. **Given** 用户浏览一个 PostgreSQL 数据库，**When** 结构树渲染该数据库或其下 Schema 节点，**Then** 除通用的 Tables、Views 分组外，还展示 PostgreSQL 专属的 Query、Functions、Procedures 分组
2. **Given** 结构树的模块展示逻辑，**When** 评审该逻辑的组织方式，**Then** PostgreSQL 专属模块的出现与否由该连接的数据库类型决定，通用树状图渲染逻辑不包含"仅 PostgreSQL 才有"的特判散落在各处
3. **Given** 项目未来新增一种不支持 Functions/Procedures 的数据库类型，**When** 该类型的连接被展示在结构树中，**Then** 树状图不显示 Query/Functions/Procedures 节点，且实现方式只需新增/调整该类型的模块配置，不修改 PostgreSQL 现有展示逻辑

---

### Edge Cases

- 用户账号在服务器上没有任何可访问数据库（权限受限）时，服务器节点展开后应提示"无可访问数据库"，而不是报错或空白
- 用户展开某个数据库/Schema 节点耗时过长或失败（网络中断、权限不足）时，仅该节点显示错误与重试入口，不影响其他已展开节点的可用性
- 同一服务器地址被配置为多条不同凭据的连接时，各连接在结构树中须独立展示各自可见的数据库范围，互不影响
- 用户连接后，服务器上的数据库被新增或删除，结构树需提供刷新入口以重新获取最新的数据库列表，而不要求用户重新创建连接
- 改造前保存的、绑定单一数据库的历史连接配置，在改造后自动升级为服务器级连接，原绑定数据库作为默认展开/激活项，用户无需手动迁移
- 非 PostgreSQL 数据库类型（当前项目尚未实现驱动）在没有 Query/Functions/Procedures 概念时，树状图不应出现空的模块占位分组

## Requirements _(mandatory)_

### Functional Requirements

**连接创建与管理**

- **FR-001**: 新建连接表单 MUST 不再要求用户在建立连接前从固定列表选择唯一的目标数据库作为连接范围限制
- **FR-002**: 保存的连接配置 MUST 代表一次服务器级连接；建立连接后，用户 MUST 能够访问该账号在此服务器上有权限查看的全部数据库，无需为每个数据库单独创建连接记录
- **FR-003**: 现有的"测试连接""仅保存""保存并连接"操作 MUST 在语义调整为服务器级后继续可用，用户操作步骤与交互方式保持不变
- **FR-004**: 用户断开一条连接时，MUST 一并断开该服务器连接下所有数据库的已加载浏览状态；重新连接后 MUST 能重新加载
- **FR-005**: 系统 MUST 提供刷新入口，允许用户在不重建连接的前提下重新获取服务器上的数据库列表及某数据库下的结构信息

**侧边栏结构树**

- **FR-006**: 侧边栏结构树 MUST 以"服务器连接 → 数据库 → 结构模块"三级为主干进行渲染，服务器节点展示连接名称、地址及连接状态
- **FR-007**: 服务器节点展开后，MUST 动态列出该服务器上用户有权限访问的全部数据库，数据来源于对数据库驱动的实时查询，而非静态配置
- **FR-008**: 数据库节点展开后，MUST 通过数据库驱动实时获取并展示该数据库下的结构分组（如 Schema、表、视图等通用模块），仅在用户实际展开该节点时才发起对应的数据请求（按需加载）
- **FR-009**: 结构树的每个可展开节点 MUST 独立维护自己的加载中/已加载/加载失败状态，单个节点的加载失败不得影响其他节点的展示与交互
- **FR-010**: 对于支持"Query""Functions""Procedures"等专属模块的数据库类型（当前为 PostgreSQL），结构树 MUST 在对应数据库/Schema 层级展示这些专属分组，且展示位置与设计参考图一致
- **FR-011**: 对于不支持上述专属模块的数据库类型，结构树 MUST NOT 展示这些专属分组或其空占位
- **FR-012**: 结构树中"某数据库类型支持哪些专属模块"的定义方式 MUST 与通用树状图渲染逻辑解耦，新增一种数据库类型的专属模块 MUST 只需新增/调整该类型自身的模块配置，不需要修改已支持类型（如 PostgreSQL）的现有展示逻辑
- **FR-013**: 结构树 MUST 支持逐层展开/收起，用户在同一会话内的展开状态与已连接服务器/数据库保持关联，切换其他连接或数据库后再切回时不丢失该连接下的浏览位置

**功能连续性**

- **FR-014**: 现有的数据浏览能力（点击/双击表、视图节点打开数据预览）MUST 在服务器级连接模型下保持可用，行为与调整前一致
- **FR-015**: 现有的查询执行能力（在指定数据库/Schema 上下文中执行 SQL）MUST 在服务器级连接模型下保持可用，用户仍可明确知道当前查询作用于哪个数据库
- **FR-016**: 改造前保存的历史连接配置（绑定单一数据库）MUST 在不需要用户任何手动操作的情况下自动升级为服务器级连接：原本绑定的数据库作为该连接下的默认展开/激活数据库，用户可继续正常使用该连接并立即看到服务器上的其他数据库

### Key Entities _(include if feature involves data)_

- **服务器连接（Server Connection）**: 用户配置并建立的一次数据库服务器级连接，包含地址、端口、认证信息、所属数据库类型与连接状态；一条服务器连接可关联多个数据库
- **数据库（Database）**: 归属于某条服务器连接下、用户有权限访问的一个具体数据库实例，是结构树的第二级节点
- **结构模块（Schema Module）**: 数据库下的一个功能分组，包含通用模块（如 Schema、表、视图）与数据库类型专属模块（如 PostgreSQL 的 Query、Functions、Procedures）
- **数据库类型能力集（Database Type Capability）**: 定义某种数据库类型支持哪些专属结构模块及其在树状图中的展示位置，是实现"专属模块隔离与可扩展架构"的核心配置依据

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 用户访问同一服务器上的多个数据库时，只需创建 1 条连接配置，无需为每个数据库单独创建连接（对比调整前，连接配置数量随可访问数据库数量线性增长）
- **SC-002**: 连接成功后，服务器上用户有权限访问的数据库在侧边栏的可见覆盖率达到 100%
- **SC-003**: 对照参考设计图走查 PostgreSQL 服务器连接的结构树，服务器、数据库、Query/Schema/Tables/Views/Functions/Procedures 各层级节点的层级关系与展示位置 100% 还原
- **SC-004**: 展开服务器或数据库节点后，在网络与服务器状态正常的情况下，结构信息在 3 秒内完成加载或明确进入错误态，不出现无反馈的长时间空白
- **SC-005**: 改造完成后，对查询执行、数据浏览、连接管理三类既有功能进行走查验证，功能可用性 100% 保持，不出现因连接模型调整导致的功能回退
- **SC-006**: 新增一种数据库类型的专属模块配置时，改动范围只涉及该类型自身的配置，不触及已支持类型（PostgreSQL）现有的结构树展示代码路径

## Assumptions

- 当前项目仅实现 PostgreSQL 数据库驱动，其他数据库类型的实际接入将在后续阶段完成；本特性只要求为其预留架构上的可扩展性，不要求本期交付第二种数据库类型
- "服务器级连接"下可访问的数据库范围，以该连接使用的账号在数据库服务器上被授予的权限为准，无权限的数据库不在树状图中展示
- 结构树中的"Query"模块特指浏览入口/快捷方式，用于在对应数据库或 Schema 的上下文中快速开始一次查询；具体 SQL 编辑与执行能力由现有查询功能提供，本特性只涉及该入口在结构树中的展示与归类
- 参考设计图中的具体图标、颜色、间距等视觉样式作为交互还原的参考基准，非本规格要求的像素级验收标准
- 结构树各节点的数据默认按需加载（用户展开时才请求），以避免一次性拉取整台服务器所有数据库结构造成的性能问题
- 系统建立底层连接时可能需要指定一个初始数据库用于建立会话（例如管理型数据库），该默认数据库的选择策略属于实现细节，不在本规格约束范围内
