# Feature Specification: AI Agent 多轮对话与本地记忆化存储

**Created**: 2026-08-14

**Status**: Draft

## Clarifications

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 在同一个对话线程中连续多轮交互 (Priority: P1)

用户在 Code 模式下完成第一轮指令后，不关闭当前对话，继续输入后续指令（如"帮我查一下 users 表的结构" → 拿到结果后追问"那 orders 表呢？"），Agent 能够记住前文中的上下文（已知的数据库连接、之前查过的表、讨论过的字段），无需用户在每轮指令中重复提供已告知的信息。

**Why this priority**: 这是多轮对话的核心价值——将 Agent 从"一次性问答工具"升级为"可连续协作的工作伙伴"。没有这一能力，后续的对话管理、历史记录持久化都失去了最根本的使用场景。

**Independent Test**: 在 Code 模式下先输入一条指令完成一轮对话，再紧接着输入一条引用前文内容的指令（如"把刚才那张表的索引也查一下"），验证 Agent 能正确理解指代并基于前文上下文执行操作，全程无需用户重复说明数据库连接或表名等已在前文中提供的信息。

**Acceptance Scenarios**:

1. **Given** 用户在同一对话中刚完成了一轮完整的指令（Agent 已返回最终结果），**When** 用户在同一对话输入框中输入引用前文内容的新指令（如"把刚刚那张表的所有索引列出来"），**Then** Agent 正确理解"刚刚那张表"指的是上一轮操作涉及的表，并基于已有的数据库连接和表信息进行推理，无需用户再次指定连接或数据库。
2. **Given** 用户在同一对话中已进行多轮交互，**When** 用户输入一条与前文无关的新指令（如前面在讨论表结构，新指令要求执行某条 SQL），**Then** Agent 能沿用前文中的数据库连接上下文执行新指令，而非当作一次全新的无上下文任务。
3. **Given** 一个包含了多轮交互的对话，**When** 用户在任一时刻查看对话历史，**Then** 系统以清晰的时间线展示所有历史消息（用户指令、Agent 思考/工具调用摘要、最终回复），支持滚动浏览。
4. **Given** 一个对话已包含多轮交互，**When** 用户开启一个新的对话，**Then** 新对话不与旧对话共享上下文——新对话中的 Agent 不会引用旧对话中的表名或操作结果。

---

### User Story 2 - 重新打开应用后恢复之前的对话并继续 (Priority: P2)

用户在一次使用会话中与 Agent 进行了多轮有意义的交互，中途关闭应用或切换到其他功能。当用户再次打开应用进入 Code 模式时，能够在最左侧可折叠的"对话历史"面板中看到之前进行过的对话列表，选择某一对话后可以查看完整的历史消息，并且可以从中断处继续向 Agent 发送新指令，Agent 能够基于之前的完整对话历史继续推理。

**Why this priority**: 对话持久化是多轮对话从"会话内记忆"升级为"跨会话记忆"的关键一步。没有持久化，用户的对话在工作台切换或应用重启后就丢失了。但它在 P2 而非 P1，因为即便没有持久化，单次会话内的多轮对话（P1）已经能覆盖大量使用场景。

**Independent Test**: 进行一次完整的多轮对话后，关闭应用并重新启动，进入 Code 模式，验证对话列表中出现了之前的对话记录（含标题和时间），点击进入后能看到完整的历史消息，继续发送新指令时 Agent 能基于历史上下文正确推理。

**Acceptance Scenarios**:

1. **Given** 用户完成过一次或多次 Agent 对话（含单轮和多轮），**When** 用户重启应用后进入 Code 模式，**Then** 系统在最左侧可折叠的"对话历史"面板中展示之前所有对话的列表，每条显示自动生成的简要标题和最后更新时间。
2. **Given** 对话列表中存在多条历史对话，**When** 用户点击选择其中一条，**Then** 系统加载并展示该对话的完整消息历史，用户可继续发送新指令，且新指令会自动追加到该对话的消息序列中。
3. **Given** 用户选中一条历史对话并继续发送了新指令，**When** 新指令执行完毕后退出 Code 模式并再次进入，**Then** 该对话的更新时间和消息内容均已包含最新一轮交互的结果。
4. **Given** 用户对某条不再需要的对话执行删除操作，**When** 确认删除后，**Then** 该对话及其所有关联消息从对话列表和存储中永久移除，不可恢复。

---

### User Story 3 - 对话记录的存储与访问不影响应用整体性能 (Priority: P3)

无论用户累积了多少条历史对话和消息，应用的启动速度、对话切换流畅度、Agent 响应延迟不受影响。对话记录的读写操作对用户不可见的后台完成，不会出现"加载中"卡顿或 UI 冻结。

**Why this priority**: 性能是"最高性能最佳实践"要求的核心体现。性能问题在对话数量较少时不易察觉，但随着使用时间增长会逐渐凸显并损害用户体验。放在 P3 是因为性能优化必须在功能完整（P1/P2）之后才能进行有效的针对优化，但架构设计必须从一开始就考虑到性能约束。

**Independent Test**: 构造大量历史数据（如 100 条对话、10000 条消息）的场景，验证应用启动耗时、对话列表滚动流畅度、对话切换响应时间三项指标均不超过数据量较小时的 2 倍。

**Acceptance Scenarios**:

1. **Given** 用户有大量历史对话记录（例如 50 条以上对话），**When** 用户进入 Code 模式查看对话列表，**Then** 对话列表在 500ms 内完成加载并可供交互。
2. **Given** 用户正在查看一条包含上百条消息的长对话，**When** 用户滚动浏览历史消息，**Then** 滚动过程保持流畅，无可见卡顿或大量空白加载区域。
3. **Given** 用户正在对话中等待 Agent 回复，**When** 系统同时执行对话记录的持久化写入，**Then** Agent 响应速度不受持久化操作影响——持久化在后台异步完成，不阻塞推理流程或 UI 更新。
4. **Given** 应用累积了大量历史数据，**When** 应用启动，**Then** 启动耗时与无历史数据时相比增加不超过 50%。

---

### Edge Cases

- 用户在一轮对话的执行过程中（Agent 正在推理/调用工具）切换到了另一条历史对话：系统中断当前执行，将已完成的工具调用结果和部分推理状态保存到对话记录中，用户切回对话后可查看已有的部分结果并选择是否继续发送新指令（新指令将使 Agent 基于已保存的上下文继续推理）。
- 用户在一轮对话处于等待工具确认状态（`paused_for_confirmation`）时切换到另一条对话：当前对话保持等待确认状态不变，用户切回后仍需对之前的工具调用做出确认或拒绝。
- 对话列表中的历史对话数量达到上百条时，列表的加载和渲染策略如何保证不阻塞 UI？
- 单条对话的消息数量达到上千条时，完整加载到上下文中会不会超出 LLM 的上下文窗口？如何管理上下文窗口？
- 用户的对话历史存储在本地磁盘，数据文件损坏或磁盘空间不足时如何处理？
- 两个对话之间是否存在"共享记忆"（如用户在某条对话中提到的偏好，能否被其他对话感知）？
- 如果用户在历史对话中引用了一个已经断开或已删除的数据库连接，Agent 如何应对？
- 当用户首次使用 Agent 功能或已删除所有历史对话后，"对话历史"面板为空：展示引导性提示文案和"新建对话"入口，引导用户开始第一次对话。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 支持在同一对话会话内进行多轮连续交互：每轮交互中，Agent 能够访问该对话之前全部轮次的用户指令、Agent 回复和工具调用记录作为推理上下文，实现跨轮次记忆。
- **FR-002**: 系统 MUST 将每一轮交互（用户指令 + Agent 执行结果）以消息形式追加到对话的消息序列中，消息序列按时间先后排列，支持多轮累积。
- **FR-003**: 系统 MUST 支持创建新的对话实例，新对话以空白状态开始，不与任何已有对话共享上下文。
- **FR-004**: 系统 MUST 将对话及其中所有消息持久化到本地存储，使数据在应用重启后仍然可用且完整（包括消息内容、工具调用记录、对话元数据）。
- **FR-005**: 系统 MUST 在 Code 模式最左侧提供可折叠的"对话历史"面板——该面板替换当前"任务列表-实例项目"占位区域；面板内展示所有已持久化的活跃对话，每条对话至少显示自动生成的标题和最近更新时间，支持按更新时间倒序排列。
- **FR-006**: 系统 MUST 支持从对话列表中选择并加载某条历史对话的完整消息历史，加载后可继续向该对话发送新指令。
- **FR-007**: 系统 MUST 支持删除历史对话操作，删除后该对话及其所有关联消息从存储和列表中永久移除。
- **FR-008**: 系统 MUST 支持对话的手动归档与取消归档：用户可通过右键菜单将活跃对话归档（移入"已归档"分组），也可将已归档对话恢复为活跃状态；归档不删除数据，仅改变对话在面板中的可见性分组。
- **FR-009**: 系统 MUST 保证对话数据的持久化写入采用完全异步方式执行，不阻塞 Agent 推理循环、IPC 通信和 UI 渲染线程。
- **FR-010**: 对话持久化存储方案 MUST 支持高效的增量追加写入——每次新增一轮对话消息时，仅写入增量部分而非重写整个对话文件，确保单轮交互的持久化开销为 O(1) 而非 O(n)。
- **FR-011**: 系统 MUST 支持对超过上下文窗口限制的长对话进行智能上下文裁剪——当对话历史消息过长时，自动裁剪早期消息以适配 LLM 上下文窗口，但完整消息历史在本地存储中不受裁剪影响。
- **FR-012**: 对话列表的加载 MUST 采用分页或增量加载策略，确保列表视图在历史对话数量较多时（≥100 条）仍能在可感知的短时间内完成首屏渲染。
- **FR-013**: 长对话的消息历史加载 MUST 采用按需加载策略——仅加载当前视口附近的消息内容，确保无论对话消息总量多大，单次加载的数据量和渲染开销始终可控，避免一次性加载全部消息导致的性能问题。
- **FR-014**: 对话标题 MUST 基于首条用户指令的内容自动生成（如截取前 N 个字符或通过 Agent 生成简短摘要），用户无需手动命名。
- **FR-015**: 系统 MUST 在对话执行过程中自动将当前对话状态持久化（包括进行中的 AgentRun 中间状态），以应对应用异常关闭导致的数据丢失；恢复后对话应处于可继续或可查看的状态。
- **FR-016**: 系统 MUST 在用户切换对话时中断当前对话中正在执行的 Agent 任务——将已完成的部分结果保存到对话记录中，用户切回后可在已有结果基础上继续；处于等待工具确认状态的对话在切换时保持不变，用户切回后继续等待确认。
- **FR-017**: 存储层 MUST 对数据文件损坏具备容错能力：存储初始化时检测文件完整性，损坏时使用备份或重建空存储，确保应用不会因存储层异常而无法启动。
- **FR-018**: "对话历史"面板在无任何对话记录时 MUST 展示空状态引导：包含简短的引导文案说明功能用途和一个醒目的"新建对话"操作入口，帮助新用户或清空后的用户快速开始。

### Key Entities _(include if feature involves data)_

- **对话（Conversation）**: 用户与 Agent 之间的一次完整对话线程。包含属性：唯一标识符、自动生成的标题、创建时间、最后更新时间、状态（活跃/已归档）。一个对话包含多条消息。活跃对话在"对话历史"面板主列表中展示；已归档对话被移入"已归档"分组，不在主列表中显示但保留完整数据，可随时取消归档恢复。
- **消息（Message）**: 对话中的一条记录，对应一轮交互。包含属性：唯一标识符、所属对话标识符、消息角色（用户/Agent）、消息内容、关联的工具调用记录列表、创建时间戳、序列序号（在对话内的顺序）。
- **工具调用记录（Tool Call Record）**: 沿用 008 号功能的 `AgentToolCallRecord` 结构，作为消息的子级数据嵌入存储。一次 Agent 回复消息可能包含多个工具调用记录。
- **对话元数据索引（Conversation Index）**: 所有对话的轻量级索引文件，仅包含每条对话的标题、标识符、时间戳等摘要信息，供对话列表视图快速加载，不包含完整的消息内容。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 用户能够在同一对话中连续交互 5 轮以上，Agent 正确引用前文信息，无需用户重复提供已告知的数据库连接或表名等上下文。
- **SC-002**: 应用重启后，所有历史对话 100% 可恢复，无数据丢失。对话列表在 500ms 内完成首屏渲染。
- **SC-003**: 在累积 100 条对话、平均每条对话 20 条消息的规模下，单轮新消息的持久化写入耗时不超过 50ms，且不会阻塞 Agent 推理响应。
- **SC-004**: 在 100 条对话的数据规模下，应用冷启动耗时与零数据状态相比增幅不超过 50%。
- **SC-005**: 对话列表滚动和长对话消息浏览全程无明显卡顿（帧率不低于 30fps），用户感知不到因历史数据规模增长而引起的性能下降。
- **SC-006**: 用户无需任何手动操作即可在切换对话、重启应用后恢复到之前的对话状态并继续交互——整个过程自动完成，用户仅需点击对话即可。

## Assumptions

- 对话存储为纯本地存储，不涉及云端同步或多设备同步。用户在一台设备上的对话历史不会出现在另一台设备上。
- 对话之间完全隔离，不存在跨对话的共享记忆或用户偏好继承。如果未来需要跨对话记忆能力，将作为独立功能单独规划。
- 上下文窗口管理基于 LLM 的 token 限制进行裁剪，裁剪策略为"从最早的消息开始丢弃，保留最新消息"，优先保证最近对话的上下文完整性。
- 本功能基于 008 号功能（Code 模式 Agent 化改造）已实现的架构基础进行开发，复用其 `AgentMessage`、`AgentRun`、`IPC 通道`等预留扩展点。008 号功能中 `AgentRun.history` 字段和 `AgentMessage` 类型即为本功能的前置设计。
- 应用的存储方案遵循项目宪法中推荐的 `electron-store` 作为本地持久化方案，对话列表索引与消息正文分层存储以优化读写性能。
- 对话的自动标题生成采用简单规则（截取首条用户指令的前 50 个字符），不依赖额外的模型调用，保证标题生成为零延迟操作。
- 本功能为单用户本地应用场景，不涉及用户认证、权限隔离或多租户数据分离。
