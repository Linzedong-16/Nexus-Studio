# Feature Specification: 内存占用优化：查询结果与对话历史管控

**Feature Branch**: `010-memory-optimization`

**Created**: 2026-08-17

**Status**: Draft

**Input**: User description: "P0~P3全部解决，完成内存优化对于历史对话无上限问题，默认达到40轮对话要给用户最底部提示下建议用户创建新对话"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 大结果集查询不拖累应用运行 (Priority: P1)

用户在查询窗口执行一条未加行数限制的查询（例如误写的 `SELECT *` 未加 `LIMIT`，返回十万甚至更多行），应用能够在不出现明显卡顿、内存占用异常飙升甚至崩溃的前提下正常展示查询结果，并让用户清楚知道结果已经被限制展示范围，如需查看全部数据可以通过导出获取。

**Why this priority**：这是当前内存占用问题中风险最高的一环——任意一次误操作的大查询都可能让应用内存瞬间飙升，进而拖慢甚至冻结整个应用，影响用户对其他标签页/连接的正常使用。解决这一问题收益最大，也最直接地保护了应用的可用性下限。

**Independent Test**：连接一个包含十万行以上数据的表，执行不带 `LIMIT` 的全表查询，验证应用不出现明显卡顿或内存异常飙升，结果区域正常展示且明确提示"已截断"及获取完整数据的方式。

**Acceptance Scenarios**:

1. **Given** 用户在查询编辑器中输入一条会返回超大数据量（超过系统设定上限）的查询，**When** 用户执行该查询，**Then** 系统正常返回结果、正常展示上限内的数据行，并在结果区域给出明显提示，说明结果已被截断以及如何获取完整数据。
2. **Given** 一条查询返回的数据行数在系统设定上限以内，**When** 用户执行该查询，**Then** 结果正常完整展示，不出现任何截断提示。
3. **Given** 用户看到了"结果已截断"的提示，**When** 用户使用提示中提供的导出入口，**Then** 用户可以获取到该查询对应的完整数据，不受预览行数上限的限制。

---

### User Story 2 - 同时打开多个查询标签页不会让内存持续攀升 (Priority: P2)

用户在同一个工作区中，为了对比或并行处理，先后打开多个查询标签页并各自执行过查询，又切换到其他标签页继续工作、长时间不关闭这些旧标签页。整个过程中，应用整体内存占用不会因为这些未主动关闭、也不再查看的标签页持续、无限制地累积增长。

**Why this priority**：用户很少会及时关闭标签页，未关闭标签页里驻留的历史查询结果是导致内存随使用时长稳步上升的第二大来源。相比 P1 的"单次操作即可触发的尖峰风险"，这类问题是"长期使用下的稳步劣化"，同样重要但相对不那么紧急。

**Independent Test**：依次打开 5 个标签页并在每个标签页执行一次返回较多数据的查询，切换到最早打开的标签页之外的位置，保持应用运行一段时间后观察内存占用趋势，验证内存不会随时间持续攀升；重新切回最早的标签页，验证用户仍能获得可用的查询结果（或明确的重新获取指引）。

**Acceptance Scenarios**:

1. **Given** 用户打开了多个标签页且均已执行过查询，**When** 用户长时间停留在其中一个标签页、不再查看其余标签页，**Then** 其余长期未被查看的标签页所占用的内存会被系统自动回收，应用整体内存占用不会因这些闲置标签页持续增长。
2. **Given** 一个标签页的查询结果已被系统自动回收，**When** 用户重新切换回该标签页，**Then** 系统明确告知用户结果已释放，并提供便捷的方式让用户重新获得该查询的结果（如一键重新执行）。
3. **Given** 用户正在当前激活的标签页中查看或操作查询结果，**When** 系统执行内存回收逻辑，**Then** 当前激活标签页的查询结果不会被回收，用户的操作不受任何影响。

---

### User Story 3 - 切换或不再使用某个数据库后，相关连接资源及时释放 (Priority: P3)

用户在同一个数据库连接下，先后浏览了多个不同的数据库（例如先看 db_a 又看 db_b），并逐一关闭了对应数据库的所有标签页。系统能够识别出某个数据库已经不再被任何打开的标签页使用，并主动释放该数据库对应的后台连接资源，而不是等到用户断开整个连接时才统一释放。

**Why this priority**：相比 P1/P2 涉及的查询结果数据体量，单个数据库连接资源本身占用相对有限，但在用户长期不断开连接、频繁切换浏览多个数据库的场景下，这部分资源会持续累积。优先级低于结果集内存问题，但仍应纳入本次统一治理。

**Independent Test**：在同一个连接下依次打开 db_a、db_b 两个数据库各自的标签页并执行查询，关闭 db_a 下的所有标签页（保留 db_b 的标签页打开），验证 db_a 对应的后台连接资源被释放，同时 db_b 的标签页仍可正常查询、不受影响。

**Acceptance Scenarios**:

1. **Given** 用户在同一连接下同时打开了多个数据库各自的标签页，**When** 用户关闭某个数据库对应的所有标签页（该数据库下已无任何打开的标签页），**Then** 系统释放该数据库对应的后台连接资源，同时其他数据库的标签页和连接资源不受任何影响。
2. **Given** 用户关闭了某个数据库的部分标签页、但仍有该数据库的其他标签页处于打开状态，**When** 关闭动作发生，**Then** 系统不会释放该数据库对应的连接资源，因为仍有标签页依赖它。
3. **Given** 某数据库对应的连接资源已被释放，**When** 用户重新打开该数据库的标签页并执行查询，**Then** 系统自动重新建立所需的连接资源，用户无需感知或手动干预。

### User Story 4 - 长对话在达到一定轮次后提醒用户新建对话 (Priority: P4)

用户与 AI 助手在同一个对话中持续进行多轮交互（提问、工具调用、追问）。当该对话累积的轮次达到系统设定的默认阈值（40 轮）时，系统在对话界面最底部给出明显但不打断当前操作的提示，说明当前对话已经进行了较多轮次，建议用户创建一个新对话，以获得更流畅的体验。

**Why this priority**：相比前三项直接影响内存占用峰值和稳态水平的问题，超长对话历史带来的内存增长相对缓慢、影响范围较窄（仅限重度使用 AI 功能且长期不新建对话的用户）。将其设为最低优先级，采用"提示引导用户主动新建对话"的轻量方式，而非强制截断或隐藏历史，兼顾了内存治理与用户对完整对话记录的知情权。

**Independent Test**：与 AI 助手在同一个对话中连续完成 40 轮及以上的交互，验证在达到第 40 轮时对话界面最底部出现建议新建对话的提示；在未达到 40 轮之前的任意时刻，验证该提示不会出现。

**Acceptance Scenarios**:

1. **Given** 用户在同一个对话中已完成的交互轮次达到系统设定的默认阈值（40 轮），**When** 该对话界面处于当前显示状态，**Then** 系统在对话界面最底部展示提示，建议用户创建新对话，且提示内容清晰、不遮挡用户的正常输入操作。
2. **Given** 用户在同一个对话中已完成的交互轮次尚未达到 40 轮，**When** 用户查看该对话界面，**Then** 界面底部不出现任何关于对话轮次或新建对话的提示。
3. **Given** 提示已经出现，**When** 用户点击提示中的"新建对话"入口，**Then** 系统创建一个新的空白对话并切换到该对话，原对话的完整历史记录保持不变、可随时通过对话列表重新查看。
4. **Given** 提示已经出现，**When** 用户选择忽略提示并继续在当前对话中发送新指令，**Then** 系统正常处理该指令，不阻止或限制用户继续在原对话中交互，提示保持展示直到用户新建对话或手动关闭提示。

---

### Edge Cases

- 用户执行的查询本身就是为了获得精确的统计结果（如 `COUNT` 类聚合查询），结果截断不应影响这类查询本身返回的单一数值结果的正确性。
- 用户在结果被截断的提示出现后，未使用导出功能，而是缩小查询范围重新执行（加上 `WHERE` 或 `LIMIT`）：系统应按新查询正常执行，若新结果仍超过上限才再次提示，否则不再提示。
- 用户在某个标签页的结果刚好处于系统判定"可以回收"的临界时间点重新切回该标签页，需要保证不会出现结果已被回收但界面未及时提示的空白体验。
- 用户不逐个关闭标签页，而是直接关闭整个应用：数据库连接资源的释放应等价于连接断开时的整体释放，不受本次改动影响。
- 对话轮次提示的判断以"当前对话"为单位：用户新建对话后在新对话中继续交互直至再次达到 40 轮，提示应在新对话下重新独立出现。
- 用户在对话轮次提示出现后既不新建对话也不主动关闭提示，长时间保持当前状态：提示应持续存在，不因为时间流逝或界面刷新而自行消失（除非用户已新建对话）。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 对任意一次查询返回的数据行数设置默认上限（默认 5 万行）；当查询实际结果行数超过该上限时，仅保留上限内的行数用于展示，其余行不加载到内存或界面中。
- **FR-002**: 当查询结果被截断时，系统 MUST 在结果展示区域明确提示用户结果已被截断、已展示的行数与上限，并说明可以通过导出等方式获取完整数据。
- **FR-003**: 导出功能 MUST 不受预览行数上限的限制，用户可以导出该查询对应的完整数据集。
- **FR-004**: 系统 MUST 能够识别工作区中连续处于非激活（未被用户查看）状态超过默认时长（10 分钟）的查询标签页，并在满足条件后自动释放其已保存的查询结果数据，仅保留恢复查询所需的必要信息（如查询语句本身）。
- **FR-005**: 系统 MUST 保证当前激活的查询标签页的结果始终可用，不被自动释放逻辑影响。
- **FR-006**: 当用户切换回一个已被释放结果的标签页时，系统 MUST 明确告知用户结果已释放，并提供简单直接的方式（如一键重新执行）帮助用户重新获得结果。
- **FR-007**: 系统 MUST 能够识别某个数据库在当前连接下是否仍有任何打开的标签页在使用；当某数据库对应的所有标签页均已关闭时，系统 MUST 释放该数据库对应的后台连接资源。
- **FR-008**: 释放某个数据库的连接资源 MUST 不影响同一连接下其他仍在使用中的数据库的正常查询能力。
- **FR-009**: 当用户重新访问一个连接资源已被释放的数据库时，系统 MUST 自动重新建立所需资源，整个过程对用户透明，不需要用户手动操作或重新配置连接。
- **FR-010**: 系统 MUST 统计每个对话内已完成的交互轮次；当轮次达到默认阈值（40 轮）时，MUST 在该对话界面最底部展示提示，说明当前对话轮次较多并建议用户创建新对话。
- **FR-011**: 该提示 MUST 不阻止或限制用户继续在当前对话中发送新指令；用户忽略提示后仍可正常使用当前对话的全部功能。
- **FR-012**: 提示 MUST 提供直达"新建对话"操作的入口；用户点击后系统创建并切换到一个新的空白对话，原对话的完整历史记录保持不变，可随时通过对话列表重新访问。
- **FR-013**: 对话轮次的统计 MUST 针对每个对话单独计算；用户新建对话后，新对话的轮次计数从零重新开始，达到阈值后同样会在该对话下独立展示提示。
- **FR-014**: 在对话轮次未达到默认阈值之前，系统 MUST NOT 展示新建对话相关提示。

### Key Entities _(include if feature involves data)_

- **查询结果（Query Result）**: 一次查询执行后返回的数据集合，包含实际数据行、是否被截断的标记、已加载行数与总行数（如可获取）等信息，与所属查询标签页关联。
- **查询标签页（Workspace Tab）**: 用户在工作区中打开的一个独立查询窗口，拥有自己的查询语句、执行结果、激活/非激活状态；标签页关闭时其关联的查询结果和资源引用一并清理。
- **数据库连接资源（Database Connection Resource）**: 某个数据库连接下、按具体数据库维度建立的后台访问资源，供该数据库下所有已打开的标签页共享使用；当某数据库不再被任何标签页使用时可被释放，需要时可重新建立。
- **对话（Conversation）**: 用户与 AI 助手之间的一次连续交互线程，包含多轮交互记录；本功能新增"当前轮次数"这一可衡量属性，用于判断是否达到提示阈值。
- **对话轮次提示（Conversation Length Notice）**: 当对话轮次达到默认阈值后，在对话界面底部展示的引导性提示，包含说明文案和新建对话的操作入口。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 执行任意一次返回数据行数远超默认上限（5 万行，例如实际有十万行以上）的查询，应用响应查询请求、展示结果的耗时和内存占用峰值，应与执行一次刚好等于上限行数（5 万行）的查询相比处于同一量级，不随实际数据量的进一步增大而继续升高。
- **SC-002**: 用户可以在结果被截断提示出现后的任意时刻，通过导出操作获取到 100% 完整的原始数据，数据完整性不受预览上限影响。
- **SC-003**: 在打开 5 个以上查询标签页且长时间（超过默认释放时长 10 分钟）只聚焦其中 1 个的使用场景下，应用整体内存占用相比"同时保持全部标签页结果都可用"的情况明显降低，且不随应用运行时长的进一步增加而持续攀升。
- **SC-004**: 用户重新切回一个结果已被释放的标签页后，能够在一次操作（如点击一个按钮）内重新获得可用的查询结果，无需重新配置连接或重新输入查询语句。
- **SC-005**: 在同一连接下浏览多个数据库并逐一关闭对应标签页后，已关闭数据库对应的后台资源全部被释放，仅保留仍在使用的数据库对应的资源；应用在该场景下的资源占用与"只连接过当前仍在使用的数据库"的情况基本一致。
- **SC-006**: 任意对话在达到第 40 轮交互时，100% 会在界面最底部出现建议新建对话的提示；在未达到 40 轮之前，该提示 100% 不会出现。
- **SC-007**: 用户忽略对话轮次提示继续对话，不会遇到任何功能限制或额外的操作阻碍；系统响应速度与轮次提示出现前保持一致。

## Assumptions

- 查询结果预览行数的默认上限（5 万行）、标签页非激活后释放结果的默认时长（10 分钟），均采用系统内置的合理默认值，不对用户开放调整入口；如后续有明确的自定义需求，可作为独立功能扩展。
- 对话轮次阈值默认固定为 40 轮，不作为用户可配置项——这是用户在本次需求中明确给出的验收标准。
- 对话轮次以"轮"为最小计数单位，一轮指用户发出一条指令并收到 AI 助手一次完整回复（包含期间可能发生的工具调用），与已有对话历史记录的轮次概念保持一致。
- 提示一旦展示，会持续保留在对话底部，直到用户创建新对话；用户在当前对话中继续发送新指令不会使提示消失，也不会重复触发新的提示弹出行为。
- 查询结果被截断后，用户依赖的"导出获取完整数据"能力被视为已有能力的延续，本功能不改变导出功能本身的行为边界，仅确保其不受预览上限影响。
- 数据库连接资源的释放与重建仅针对同一连接下按数据库维度维护的资源，不影响用户与数据库服务器之间的整体连接（账号、密码、网络配置等）本身。
- 本功能不涉及对已有查询结果的展示样式、导出格式等做任何调整，仅聚焦于内存占用治理本身。
