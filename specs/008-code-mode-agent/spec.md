# Feature Specification: Code 模式 Agent 化改造

**Feature Branch**: `008-code-mode-agent`

**Created**: 2026-08-14

**Status**: Draft

**Input**: User description: "为项目的Code模式开发并集成agent相关功能模块，具体要求如下：

1. 功能封装：将现有Code模式下的所有操作（包括但不限于代码生成、代码分析、代码优化、错误修复等）全面封装为标准化工具（tools），每个工具需包含清晰的输入参数定义、功能描述和输出格式规范，确保agent能够正确理解和调用。
2. 对话模式：当前阶段实现单轮对话功能，用户输入指令后，agent完成一次完整的工具调用流程并返回结果；同时架构设计需预留上下文管理与多轮对话扩展接口，为后续功能升级提供支持。
3. Agent循环实现：采用标准ReAct（Reasoning and Acting）模式实现agent loop，具体包括：指令解析、思考决策（Reasoning）、工具选择、工具调用（Acting）、结果处理与响应生成等核心步骤。
4. LLM集成：集成DeepSeek大语言模型作为agent的推理核心，在项目中预留.env配置文件接口，用于后续填入DeepSeek官方API密钥，确保模型调用功能的可配置性。
5. 测试安排：测试部分由用户自行实现，开发方需提供必要的测试接口和文档支持，确保agent功能模块具备可测试性。"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 通过一句话指令完成一次完整的辅助任务 (Priority: P1)

用户在 Code 模式的对话输入框中用自然语言描述需求（例如"帮我把这条查询优化一下"或"这段 SQL 报错了，帮我修一下"），Agent 自动理解意图、选择并调用合适的工具（如生成 SQL、分析结构、优化查询、修复错误等），完成一次完整流程后，将思考过程摘要、调用了哪些工具以及最终结果一次性返回给用户。

**Why this priority**: 这是整个功能的核心价值——用户不再需要手动拆解任务、逐步调用功能，而是通过自然语言一次性获得结果。没有这一能力，其余需求（工具封装、LLM 集成）都失去了落地场景。

**Independent Test**: 在 Code 模式下输入一条明确的自然语言指令，验证系统能够返回包含"使用了哪些工具"和"最终结果"的完整回复，且过程中无需用户二次输入即可视为完成一次任务。

**Acceptance Scenarios**:

1. **Given** 用户在 Code 模式输入框中输入一条自然语言指令，**When** 用户提交该指令，**Then** 系统展示 Agent 的推理过程（选择了哪些工具、传入了什么参数）与最终结果，且整个过程无需用户中途介入。
2. **Given** 一条指令需要连续调用多个工具才能完成（例如先分析表结构、再生成 SQL、再校验语法），**When** Agent 执行该指令，**Then** 系统按顺序完成所有必要的工具调用，并在最终回复中给出统一、连贯的结果，而不是逐条展示未整合的原始输出。
3. **Given** 用户的指令模糊或缺少必要信息（例如"优化一下"但未指明优化对象），**When** Agent 无法确定应调用的工具或参数，**Then** 系统明确告知用户需要补充哪些信息，而不是猜测执行或报错崩溃。
4. **Given** 用户的指令需要执行会修改数据或表结构的操作（例如"帮我把这条 SQL 的执行结果删除重复行"），**When** Agent 判断需要调用修改类工具，**Then** 系统在实际执行前向用户展示将要执行的具体操作并等待显式确认，用户确认后才继续执行，用户拒绝则中止该步骤并说明后续可选项。

### User Story 2 - 开发者独立验证单个工具的行为 (Priority: P2)

负责测试该功能的用户需要在不经过完整对话流程的情况下，针对某一个已封装的工具单独提供输入参数并触发调用，检查其返回结果是否符合该工具声明的输出格式规范。

**Why this priority**: 需求中明确"测试部分由用户自行实现"，因此系统必须提供可独立测试的入口和文档，这是保障工具质量、支撑后续测试工作的前提条件，但不影响核心对话体验，优先级低于 P1。

**Independent Test**: 选择任意一个已封装的工具，绕过对话界面直接提供符合其输入参数定义的数据发起调用，验证返回结果的结构与工具文档中描述的输出格式规范一致；对工具传入非法或不完整参数，验证系统返回明确的校验错误而非静默失败。

**Acceptance Scenarios**:

1. **Given** 一个已封装的工具及其输入参数文档，**When** 开发者按文档提供合法参数直接调用该工具，**Then** 系统返回符合该工具输出格式规范的结果。
2. **Given** 同一个工具，**When** 开发者提供缺失必填参数或类型错误的输入，**Then** 系统返回明确指出问题字段的校验错误，而不是抛出未处理的异常。
3. **Given** 一份工具清单文档，**When** 开发者查阅该文档，**Then** 文档中每个工具都清楚列出名称、功能描述、输入参数（含是否必填与类型）、输出格式。

---

### User Story 3 - 通过配置文件启用真实的 DeepSeek 推理能力 (Priority: P3)

负责部署/维护该功能的用户在项目根目录的环境配置文件中填入 DeepSeek 官方 API 密钥后，Agent 的推理能力从"未配置"状态切换为可用状态，无需修改任何源代码。

**Why this priority**: 该能力决定 Agent 是否具备真实推理能力，但工具封装、Agent 循环结构、单轮对话流程等主体架构可以在密钥未配置前先行构建和验证（例如通过校验错误或占位提示体现"未配置"状态），因此优先级排在核心对话体验与工具测试能力之后。

**Independent Test**: 在未配置密钥的状态下发起一次对话，验证系统明确提示"未配置模型密钥"而不是无响应或崩溃；随后在配置文件中填入有效密钥并重启应用，验证同一操作能够触发真实的模型推理与工具调用。

**Acceptance Scenarios**:

1. **Given** 环境配置文件中尚未填入 DeepSeek API 密钥，**When** 用户在 Code 模式发起对话，**Then** 系统明确提示当前 Agent 推理能力未配置，并说明如何配置。
2. **Given** 环境配置文件中已填入有效的 DeepSeek API 密钥，**When** 用户在 Code 模式发起对话，**Then** Agent 使用该密钥调用 DeepSeek 完成推理与工具调用流程。
3. **Given** 配置文件中填入的密钥无效或已过期，**When** Agent 尝试调用模型，**Then** 系统向用户展示明确的认证失败提示，而不是暴露原始底层错误堆栈。

---

### Edge Cases

- 用户在 Agent 正在执行工具调用流程时关闭或刷新 Code 模式页面，会发生什么？
- 单次指令触发的工具调用次数是否有上限？达到上限但任务仍未完成时，系统如何响应？
- 某个工具执行成功但返回的数据量极大（例如分析一张有上千列的宽表）时，Agent 如何在最终回复中呈现，避免信息过载？
- DeepSeek 服务响应超时或被限流时，用户看到的是什么反馈？
- 用户连续快速发送多条指令（当前阶段为单轮对话）时，系统如何处理——排队、拒绝新请求，还是中断前一条？
- Agent 选择调用了一个工具，但该工具所需的前置上下文（例如尚未选择任何数据库连接）并不存在，系统如何提示？

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 将 Code 模式下与数据库/SQL 开发直接相关的辅助能力（包括但不限于：根据自然语言生成 SQL、分析表结构/Schema、优化查询、修复 SQL 错误、查看 DDL、执行查询）全部封装为可被 Agent 调用的标准化工具；不含与数据库/SQL 无关的通用编程辅助能力（如任意语言的通用代码生成、分析），此类能力不在本阶段范围内。
- **FR-002**: 每个标准化工具 MUST 定义清晰的名称、功能描述、输入参数规范（参数名、类型、是否必填、含义说明）与标准化输出格式（成功时的数据结构、失败时的错误信息结构）。
- **FR-003**: 系统 MUST 以 ReAct 模式驱动 Agent 循环，循环内 MUST 依次包含：解析用户指令、思考决策、选择工具、调用工具（Acting）、处理工具结果、生成最终响应；其中"思考决策"与"工具调用"两个阶段可根据任务复杂度重复多次，直至得出最终结果或达到终止条件。
- **FR-004**: 系统 MUST 为 Agent 循环设置明确的终止条件（例如已生成最终答案、达到最大工具调用次数、或判定当前指令无法继续处理），避免循环无限执行。
- **FR-005**: 当前阶段系统 MUST 仅支持单轮对话：用户提交一条指令后，Agent 完成一次完整的（可能包含多次工具调用的）处理流程并返回结果，返回结果前不接受同一对话的新指令。
- **FR-006**: 系统架构 MUST 预留上下文管理与多轮对话所需的扩展点（例如对话历史的记录位置、后续指令携带前序上下文的接口形态），使后续启用多轮对话时无需重新设计工具调用契约或 Agent 循环结构。
- **FR-007**: 系统 MUST 集成 DeepSeek 大语言模型作为 Agent 的推理核心，且模型调用方式 MUST 通过可替换的抽象方式接入（而非与 DeepSeek 强耦合），以便未来切换或新增其他模型提供方。
- **FR-008**: 系统 MUST 提供项目级的环境配置文件接口（`.env`），用于配置 DeepSeek 官方 API 密钥及必要的调用参数；该密钥 MUST NOT 被硬编码在源代码或提交到版本库中。
- **FR-009**: 当 DeepSeek API 密钥未配置、无效或调用失败（含超时、限流、认证失败等）时，系统 MUST 向用户展示清晰、可理解的状态提示，且不能导致界面无响应或程序崩溃。
- **FR-010**: 系统 MUST 向用户呈现 Agent 在完成一次任务过程中的工具调用记录（调用了哪些工具、传入的关键参数、每次调用的结果状态），以便用户理解结果是如何得出的。
- **FR-011**: 当某次工具调用执行失败时，系统 MUST 将失败原因反馈给 Agent 循环，使其能够据此调整后续决策（例如换用其他工具、向用户请求补充信息），而不是让整个任务流程静默中断。
- **FR-012**: 系统 MUST 为每个标准化工具提供独立于对话界面的调用入口与文档说明，使开发者/测试人员能够单独触发某个工具并核对其输入输出是否符合规范。
- **FR-013**: 系统 MUST 对工具的输入参数进行校验；当传入参数缺失必填项或类型不匹配时，MUST 返回明确指出具体问题字段的错误信息。
- **FR-014**: 系统 MUST 将工具区分为"只读类"（如生成 SQL、分析表结构、优化建议、查看 DDL 等不产生实际数据/结构变更的操作）与"修改类"（如执行 INSERT/UPDATE/DELETE、执行 DDL、导入/导出、删除等会产生实际变更的操作）；对修改类工具的调用，系统 MUST 在真正执行前向用户呈现将要执行的具体操作并获得显式确认后才可执行，只读类工具 Agent 可自主执行无需逐次确认。

### Key Entities _(include if feature involves data)_

- **对话会话（Conversation Session）**: 一次用户与 Agent 的交互单元；当前阶段每个会话对应一次单轮指令-响应流程，同时保留可扩展为多轮消息序列的结构。
- **消息（Message）**: 会话中的一条记录，包括用户输入的指令、Agent 的思考摘要、工具调用记录、以及最终返回给用户的回复内容。
- **工具定义（Tool Definition）**: 一个可被 Agent 调用的标准化能力单元，包含名称、功能描述、输入参数规范、输出格式规范。
- **工具调用记录（Tool Call Record）**: 一次具体的工具调用事件，包含所调用的工具、传入的实际参数、执行状态（成功/失败）、返回的数据或错误信息。
- **模型提供方配置（Model Provider Configuration）**: 描述 Agent 推理核心所需的配置信息，包括所使用的模型提供方（当前为 DeepSeek）、API 密钥来源（`.env` 文件）及调用相关参数。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 用户输入一条清晰、单一意图的指令后，能够在一次响应内看到完整的处理结果（包含调用了哪些工具与最终结论），无需自行拆解任务或多次追问。
- **SC-002**: 本阶段涉及的核心辅助能力（SQL 生成、表结构分析、查询优化、SQL 错误修复、DDL 查看、查询执行）100% 被封装为标准化工具，且每个工具均可被 Agent 正确识别并调用成功。
- **SC-003**: 开发者/测试人员无需启动完整对话界面，即可针对任意一个已封装的工具单独发起调用并得到与文档一致的结果，工具文档覆盖率达到 100%（即每个工具都有对应的说明文档）。
- **SC-004**: 当模型密钥缺失或调用异常时，用户能够在数秒内看到清晰的状态提示，而不会遭遇界面卡死或无提示的失败。
- **SC-005**: 在工具调用失败的场景中，绝大多数情况下（而非极少数例外）Agent 能够给出可理解的后续说明或建议，而不是仅将底层原始错误直接暴露给用户。

## Assumptions

- 当前阶段仅需实现"单轮对话"：一次指令对应一次完整响应；多轮对话的存储与 UI 交互不在本阶段实现范围内，仅需保证架构上预留相应扩展点。
- "开发方需提供必要的测试接口和文档支持"理解为：开发方负责让每个工具具备可被独立调用的入口并附带说明文档；具体的自动化测试用例编写由用户自行完成，不计入本功能的交付范围。
- DeepSeek API 密钥等敏感配置仅通过本地环境配置文件提供，不纳入版本库管理，遵循项目现有的密钥安全实践。
- Agent 的使用场景为已登录本地桌面应用的单用户场景，不涉及多用户权限体系或多租户隔离。
- Agent 推理核心通过可替换的模型提供方抽象接入，当前阶段仅需要接通 DeepSeek 一种提供方，无需同时实现多个提供方。
